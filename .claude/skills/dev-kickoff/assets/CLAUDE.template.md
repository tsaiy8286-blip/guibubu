## 使用者背景

使用者完全沒有程式經驗。專有名詞第一次出現要用一句白話解釋；需要做決定時給選項、附建議與理由。改完東西要告訴使用者「去哪裡看、會看到什麼」。

## 紅線（違反任一條即停下，先取得使用者同意）

1. **先討論再動手**：新增頁面、改版面結構、加新技術前，先提案取得同意。新功能走這條路：`/dev-spec` 講清楚要做什麼並拆成任務卡（使用者核准）→ `/dev-next-card` 一次做一張 → `/dev-verify-card` 使用者親手驗收。
2. **使用者親眼看過才算完成**：AI 不得自行宣告「做好了」。每張任務卡都要經過使用者在瀏覽器親手確認。
3. **危險操作白話文確認**：刪除檔案、大量改寫、改 git 歷史前，先用白話說明「這會做什麼、影響什麼、能不能復原」，確認後才執行。
4. **網站內容都是公開的**：靜態網站的所有檔案任何人都看得到。不得把密碼、金鑰、身分證號、私人電話等資料寫進網站檔案；使用者想放時要先提醒。
5. **git 一律走 git-commit skill**：不直接下 git commit／push 指令。commit 前讓使用者確認；**push 一律等使用者明說，不主動 push**。
6. **不亂裝東西**：能用純 HTML／CSS／JavaScript 做到的，就不要引入套件或框架。真的需要外部資源（字型、圖示庫等）時，先說明用途與替代方案，經同意才加。

## 開發慣例

- `docs/SPEC.md` 是網站「應該長什麼樣、做什麼事」的唯一依據：做任何功能前先讀
- 任務卡放在 `docs/cards/{功能名}/`，一張卡一個檔案
- 進度與待辦 → 更新 `專案進度追蹤.md`；延後的事必須寫進去，不可只留在對話中
- 圖片放 `images/`，檔名用英文小寫加連字號（例如 `about-photo.jpg`），避免上線後路徑出錯
- 手機和電腦都要能正常瀏覽（響應式設計）

## 怎麼開始做事

- 想加新功能或新頁面：`/dev-spec`
- 繼續做下一張任務卡：開新對話，說「做下一張卡」或 `/dev-next-card`
- 驗收做好的卡：`/dev-verify-card`
- 想把需求問清楚：`/grill`
- 存檔或上傳：`/git-commit`
