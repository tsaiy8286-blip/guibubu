# Dev Next Card：領一張任務卡做到底

把「一張任務卡」從待做推到「使用者驗收完」。上游是 `/dev-spec`（拆好的卡），每張卡驗收用 `/dev-verify-card`。

**一個對話只做一張卡。** 任務卡的大小是照「一個對話塞得下」切的；做完一張就收尾，下一張開新對話再叫一次本 skill。

**核心分工**：AI 能自己檢查的，AI 先檢查完；使用者的時間只花在 AI 判斷不了的地方（好不好看、文字對不對）。但**通過與否永遠由使用者決定**——AI 檢查過的項目照樣列給使用者，只是標成可略過。

**使用者背景**：使用者完全沒有程式經驗。開工、完工、交驗收時都用白話說明在做什麼、去哪裡看。

**互動原則**：全程與使用者對話；遵守專案 `CLAUDE.md` 的紅線。本 skill 不覆蓋任何專案紅線。

---

## 步驟零：定位與挑卡

1. 讀入背景文件：專案 `CLAUDE.md`、`docs/SPEC.md`、`專案進度追蹤.md`。
2. 找任務卡：`docs/cards/*/`。
3. **挑卡**：
   - 使用者有指定卡號 → 以使用者為準（仍要檢查依賴，依賴的卡沒完成就停下說明）。
   - 沒指定 → 挑「狀態：待做」且依賴的卡都已完成的那張，卡號最小者優先。**直接告訴使用者挑了哪張、這張做完能看到什麼，然後開工**，不必等確認。
   - 沒有可做的卡 → 告訴使用者這批卡都做完了，問他要不要用 `/dev-spec` 規劃下一個功能。
4. **前一張卡還沒驗收**（狀態「已完成」但不是「已驗收」）→ 先提醒使用者：建議先驗那張再往下做（問題離做出來的時間越近越好修）。由使用者決定。

---

## 步驟一：施工

1. 讀入：這張卡（做完能看到什麼、驗收條件）、SPEC.md 對應段落、會改到的網頁檔案。
2. 實作。範圍以這張卡為限：屬於別張卡的事不要順手做；發現卡沒寫到但非做不可的事，先問使用者。
3. 施工紀律：
   - 純 HTML／CSS／JavaScript，不引入套件或框架（紅線 6）
   - 手機和電腦都要能正常顯示
   - 圖片還沒有的話，先用同尺寸的灰色佔位區塊，並在卡的實作備註記下「待使用者提供圖片：XX」
   - 共用的樣式放 `css/`，共用的程式放 `js/`，不要每頁各寫一份
4. 卡的「驗收條件」逐條打勾（只勾真的做到的），狀態改為「已完成」。

---

## 步驟二：AI 先把能檢查的檢查一遍（當場操作）

逐條看驗收條件，分成兩類，**先列表給使用者看一眼再動手**：

| 類型 | 例子 | 怎麼驗 |
|------|------|--------|
| AI 能驗 | 頁面打得開、該有的文字和區塊有出現、連結點了會到對的頁面、按鈕點了有反應、手機寬度下沒有內容被切掉或左右捲動、瀏覽器主控台（console）沒有錯誤 | 用瀏覽器工具打開網頁操作、截圖 |
| AI 驗不了 | 好不好看、顏色搭不搭、文字通不通順、在使用者自己的手機上看起來如何 | 留給使用者 |

**怎麼打開網頁**：

- 有瀏覽器自動化工具（例如 Playwright MCP 或 Claude in Chrome）→ 直接開 `file:///` 加上檔案完整路徑。分別用電腦寬度（約 1280px）和手機寬度（約 375px）各看一次並截圖。
- 沒有瀏覽器工具 → 讀 HTML／CSS 檢查結構與連結，但**這不算實際操作過**，覆蓋欄位不得打勾。在交驗收時跟使用者說明「這張我沒辦法實際打開檢查，請你全部看一次」。

規則：

- **記錄證據**：每一項記下「做了什麼 → 看到什麼」。沒實際打開過的不准寫成驗過。
- **驗出問題 → 當場修**（範圍在這張卡內），修完重驗；超出卡範圍的停下問使用者。
- 驗完關掉自己開的瀏覽器分頁、刪掉暫存截圖。

結果填進卡的「驗證證據」兩小節。

---

## 步驟三：跑 `/dev-verify-card`

用 Skill 工具叫 `dev-verify-card`，照它的步驟把這張卡追加進 `docs/verify/` 的驗收頁面。額外規則：

- **AI 驗過的項目照列，標成可略過**：
  - `coverage.agent.covered: true`，`how` 寫實際做了什麼、看到什麼
  - `text` 第一行加引言：`> ✅ AI 已實際打開檢查過（見覆蓋說明），可略過；有空再親手看一次。`
- **AI 驗不了的項目**：`text` 不加這行，依實際情況設 `manualOnly`、`risk`；驗收頁面會把它們排在最前面。
- 交給使用者時，**明講哪幾項一定要親手看、哪幾項可略過**，讓使用者知道最少要花多少時間。
- 然後照 `dev-verify-card` 的規定等使用者回報，不要先往下走。

---

## 步驟四：處置結果與收尾

1. 照 `dev-verify-card` 步驟四、五處置不通過項目（當場修／開新卡／延後），回填卡的驗證證據，狀態改為「已驗收」。
2. 更新 `專案進度追蹤.md`：這張卡打勾、標出下一張要做的卡。
3. 走 `git-commit` 存檔（使用者確認後才 commit）。**不主動 push**；網站有上線且使用者想更新網站時，提醒他可以說「推上去」。
4. 告訴使用者下一步，**放在整則回覆的最後一句**（完成檢核等清單放在它前面），否則使用者會不知道接著要做什麼：
   - 還有卡沒做 → 「👉 下一步：開新對話，打 `next`，做 XX 卡」
   - 這批卡全做完 → 「這個功能完成了！想加新東西就說『我要加 XX』」

## 完成檢核（結束前逐項回報 ✅/❌/不適用）

- [ ] 只做了一張卡，依賴都已完成
- [ ] 沒有引入套件或框架；手機與電腦寬度都檢查過
- [ ] 驗收條件逐條分類過（AI 能驗／AI 驗不了），AI 能驗的都實際打開過，證據是真的
- [ ] 已跑 `/dev-verify-card`；AI 驗過的項目照列並標成可略過，沒有自行宣告通過
- [ ] 使用者回報的結果都已處置，卡的驗證證據與狀態已回填
- [ ] 進度文件已更新，已走 git-commit（沒有主動 push）
