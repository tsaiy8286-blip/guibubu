# Dev Verify Card：單卡即時驗收 SOP

任務卡做完一張就驗一張，不要囤到最後。問題離它被做出來的時間越遠，越難查、越難修。

**互動原則**：全程與使用者對話。驗收結果由使用者親手產生，不可自行宣告通過。

**使用者背景**：使用者完全沒有程式經驗。驗收項要寫成「打開哪一頁 → 做什麼 → 應該看到什麼」，不要出現程式術語。

---

## 步驟零：定位

1. 確認要驗哪幾張卡。使用者沒指定 → 找 `docs/cards/*/` 裡狀態「已完成」、但還沒進驗收頁面的卡，列出來問他要驗哪些。
2. 讀入：該卡本身（含「驗收條件」與「驗證證據」兩節）、SPEC.md 對應段落、該卡實際改動的檔案。
3. 卡的狀態還是「待做」→ 停下確認：是做完忘了改狀態，還是根本還沒做。沒做完不要驗。

---

## 步驟一：確認驗收頁面存在

驗收頁面固定在 `docs/verify/`：

```
docs/verify/
  index.html   ← 外殼，從本 skill 的 assets/verify-hub.template.html 複製
  data.js      ← 驗收資料，整個專案共用一份
  results/     ← 使用者填完匯出的 JSON
```

- 不存在 → 建起來（複製外殼、建 `results/` 放 `.gitkeep`），`docs/verify/` 要進版控。
- 已存在 → **不要覆蓋 `index.html`**。

---

## 步驟二：把這張卡追加進 `data.js`

資料結構照 `assets/verify-data.example.js`。一個「功能」（`docs/cards/` 底下的一個資料夾）對應一個 `changes` 物件，裡面的 `tickets` 就是這個功能的任務卡。**追加，不是重寫**：

- 對應的功能物件不存在 → 新建一個，`id` 用功能資料夾名稱，`status: "verifying"`、`allTicketsLoaded: false`。
- 已存在 → 只往它的 `tickets` 陣列**追加這張卡**，其他卡與其他功能原樣不動（使用者可能已經填了一半，改動會讓他白填）。

### `allTicketsLoaded`：結案鎖

驗收頁面的「結案」按鈕只有在 `allTicketsLoaded: true` 時才會亮。規則：

- 這個功能資料夾裡**還有卡沒進驗收頁面** → 維持 `false`。否則驗完第一張卡，頁面就會以為整個功能都驗完了。
- 這次追加的是**這個功能的最後一張卡**（資料夾裡每張卡都已在 `tickets` 裡）→ 改成 `true`。若這個功能有 3 張以上的卡，另外追加一張 `id: "integration"`、標題「整體走一遍」的卡，放一條從首頁開始、把這批功能串起來走完的操作路徑（例如：從首頁點導覽列到作品集，點開一件作品，再回到首頁）。

### 驗收項欄位規則

- **`id` 必須穩定**：格式 `{功能名}/{卡號}/{語意鍵}`，例如 `homepage/01-header/nav-links`。**絕對不要用流水號**——使用者填到一半你重新產生時，id 一變已填的結果就全部對不上。
- **`text`**：寫成「操作步驟 → 預期看到什麼」，用 Markdown（段落、清單、粗體都可以）。
- **`spec`**：`ref` 寫對應的卡或 SPEC.md 段落，`quote` 引用那句條文。
- **`coverage.agent`**：只有 AI **實際打開網頁操作過**才填 `covered: true`，`how` 寫做了什麼、看到什麼。找不到證據就填 `false`，不准推測。`coverage.auto` 一律填 `{ covered: false, ref: "" }`（這個專案沒有自動化測試）。
- **`risk`（high／medium／low）+ `riskReason`**：互動功能、跨頁連結、AI 沒驗到的判較高；理由寫成一句人話。
- **`manualOnly` + `manualOnlyReason`**：AI 本來就判斷不了的（好不好看、文字是否通順、在使用者自己手機上的樣子）設 `true`。這類項目在頁面上排最前面。
- **`crossEnv`**：只給**真的可能因裝置而異**的項目開（例如手機版排版）。其餘一律 `false`。

驗收項來源是**這張卡的「驗收條件」**。**不要把還沒做的卡的內容寫進來**，那會讓使用者去找一個根本不存在的東西。

### 驗收項要合併，不要拆太細

使用者的時間最貴。**一條驗收項＝一條走得完的操作路徑，順路能看到的就順路一起看。**

- 前提已被涵蓋就不要再測一次：「點導覽列的『作品集』，看到作品列表」這一項本身就證明了導覽列能點，不必再獨立列「導覽列能不能點」。
- 同一條路徑上的多個預期，用清單寫在同一項裡。
- 一張卡的驗收項超過 5 條，通常就是拆太細了。

寫法範例：

```text
用電腦打開 `index.html`，點導覽列的「作品集」。

預期：
- 跳到作品集頁面，上方標題是「我的作品」
- 作品以三欄排列，每件作品都有圖片和名稱
- 導覽列的「作品集」字樣變成強調色
```

## 步驟三：交給使用者驗

> 用瀏覽器打開 `docs/verify/index.html`（直接雙擊就好），左側點這張卡。
> 每一項照著做，然後點「通過」或「不通過」，不通過的可以寫一下哪裡不對。填寫會自動存在瀏覽器裡，可以分次做完。
> 標著「✅ AI 已檢查過」的可以略過；**最上面那幾項是一定要你親眼看的**。

驗完的回收方式二選一，讓使用者自己挑：

- 項目不多 → 直接在對話裡說哪幾項不過
- 想留紀錄 → 按「匯出 JSON」，**第一次按會請你選資料夾，選 `docs/verify/results/`**

不要在使用者回報結果前就往下走。

---

## 步驟四：處置不通過的項目

逐項問使用者要怎麼處理：

- **當場修**：改動小、就在這張卡的範圍內 → 直接修，修完請使用者重看該項
- **開新卡**：範圍超出這張卡 → 在同一個功能資料夾開新卡（模板在 `../dev-spec/assets/card.template.md`），並記進 `專案進度追蹤.md`
- **延後**：記進 `專案進度追蹤.md` 的「延後的事」，並在該卡的「實作備註」註明

**不要自行判定「這個不算問題」。** 使用者說不過就是不過，最多是討論怎麼處置。

使用者寫在驗收頁面裡的意見即使不是失敗也要讀完並回應——那是他花時間寫的。

---

## 步驟五：回填卡片與收尾

1. 這張卡的「驗證證據」補上本次人工驗收的結果（哪些項目使用者親手看過、什麼時候）。
2. 卡的狀態改為「已驗收」。
3. 這是功能的最後一張卡、使用者在驗收頁面按了「結案」→ 把 `data.js` 裡該功能的 `status` 改成 `"closed"`、`closedAt` 填今天日期，並在 `專案進度追蹤.md` 把這個功能移到「已完成的功能」。
4. 提醒可以走 `git-commit` 存檔（紅線 5）。

---

## 完成檢核（結束前逐項回報 ✅/❌/不適用）

- [ ] 只驗了確實已完成的卡
- [ ] `data.js` 是追加，沒動到其他卡與其他功能
- [ ] 驗收項已合併，用白話寫成「操作 → 預期」
- [ ] `allTicketsLoaded` 依規則設定（還有卡沒進來就是 false）
- [ ] 覆蓋欄位都有真實證據，沒有猜測打勾
- [ ] 使用者親手驗收完成，結果已回收並讀完
- [ ] 不通過項目都經使用者處置（修／開卡／延後），延後的已記進進度追蹤
- [ ] 卡片「驗證證據」已回填、狀態已更新
