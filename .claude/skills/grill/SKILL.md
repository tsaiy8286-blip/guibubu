# Grill：拷問式需求訪談

對使用者的計劃、決策或想法進行不留情面的訪談，走完整棵決策樹，直到達成共識。**共識確認前不得動工。**

## 訪談紀律（六條，全程遵守）

1. **一次只問一題**。等使用者回答後才問下一題。一次丟多題會讓人無法思考。
2. **每題附上你的建議答案**，並用一句話說明理由。使用者是非工程師，給選項比開放式提問有效；涉及專有名詞時先解釋概念、優缺點、風險，再讓使用者決定。
3. **事實自己查，決策才問人**。能從環境查到的事實（檔案內容、現有程式碼、套件文件），自己去查，不要拿來問使用者。只有「取捨」才值得問。
4. **順著依賴走**。先問會影響後續答案的上游決策（例如先問「給誰用」再問「要不要帳號系統」），一條分支走完再走下一條。
5. **挑戰模糊語言**。使用者用了含糊或前後矛盾的詞（「使用者」到底指誰？「完成」的判準是什麼？），當場追問到精確為止。
6. **用具體情境施壓**。對關鍵規則發明邊界情境來測試：「如果月底 31 號跨月呢？」「如果兩個人同時改呢？」讓使用者在具體例子上做決定，不在抽象原則上表態。

## 結束方式

當你判斷決策樹已走完，做兩件事：

1. **輸出共識清單**：條列所有已確認的決策（每條一行：問題 → 決定 → 理由一句話）。
2. **請使用者確認**：「以上是我們的共識，確認無誤我才開始動工。」使用者確認後，共識清單交給後續流程（寫入 spec、專案計劃、或直接執行）。

若中途使用者說「夠了、開始吧」，尊重指令，但先把**已確認**與**未確認（採用你的建議值）**分開列出再動工，讓假設留下記錄。
